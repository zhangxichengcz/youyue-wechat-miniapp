# 我的第一个 AI 辅助开发项目

## 从一个想法开始

我想做一个微信小程序，用来预约私人会面和咨询。双方可以选择活动内容、时间和地点，确认后在活动前一天收到提醒。我还希望取消和改期能在小程序里完成，并尽量使用免费资源。

我通过与 AI 协作，把这个想法逐步拆成了页面、预约规则、身份验证、数据存储、提醒任务和部署流程。AI 参与需求梳理、代码实现、逻辑测试、部署说明和故障分析；我负责提出需求、决定体验、配置账号，以及用自己的手机验证结果。

## 已经实现的部分

- 微信原生预约页面和本机演示模式。
- 邀请、确认、婉拒、取消，以及需对方同意的改期。
- 双方时间冲突检查、权限验证和重复操作保护。
- 微信登录、签名会话和订阅提醒的服务端流程。
- Cloudflare Workers、D1 与可选 Pages 入口。
- Node.js 自动测试和代码配置检查。

## 实际遇到的问题

开发者工具里运行成功，并不意味着普通手机网络也能访问服务。项目先使用 Workers 的默认地址，手机访问失败后，又增加了通过 Service binding 连接原后台的 Pages 入口。地址是否可达和是否被微信接受，都需要实际测试。

更换服务地址后，开发者工具仍缓存旧的 request 合法域名列表。刷新域名信息后才能继续联调。

启用组件按需加载后，出现了编译辅助模块缺失与页面白屏。项目目前回退这项优化、关闭增强编译，并调整预约详情的数据读取写法。之后仍收到苹果白屏和安卓微信内部请求失败的反馈，因此补充了独立检测页，分别检查页面启动、GET 健康检查与 POST 微信登录。

后续截图确认苹果体验版的健康检查和微信登录均成功。用户进一步交叉测试，反馈 iQOO、华为、苹果可以使用，一台 OPPO 仍返回微信域名校验错误。排查范围因此缩小到这台设备的运行环境，仍不能认定所有 Android 或某个品牌均有问题，也不能把网络连通当作双方提醒已完成验收。

这些问题让我认识到，AI 生成的代码需要通过不同层次的验证：语法检查、业务逻辑测试、开发者工具、真实服务、真实手机，最后才是双方用户与消息送达测试。

## 当前状态

这是持续开发和联调中的个人作品。预约规则与提醒逻辑有自动测试覆盖，开发者工具曾成功创建、读取预约；手机兼容性、双方同步与真实提醒仍需要完成验收。仓库保留这些边界，后续会随着真实测试结果更新。

公开仓库使用演示配置，不包含我个人的生产服务地址、AppID、数据库编号或微信密钥。读者可以先体验本机演示，再使用自己的账号配置真实服务。
